📚 Process Docs — the paper trail behind every feature

Each feature flows through a fixed set of documents — from the upstream spec down to the committed plan and any decision records. The /implement skill reads some as source-of-truth and writes others as it executes; the Knowledge Graph stitches them together by edge type.

What /implement reads vs. writes

📖 Read as source of truth (Phase 1)

  • SPEC upstream days_*_features.md — acceptance criteria
  • STATUS FEATURE_STATUS.md — pick target, check state
  • DETAIL feature doc — Steps → milestones, Depends/Unblocks
  • ADR governing decisions → plan Context
  • PLAN existing plan for this feature → extend, don't restart

✍️ Write / update (Phase 2)

  • PLAN new plan — committed first on the branch
  • DETAIL check off Steps + add evidence at review
  • STATUS flip the row to ✅ — same branch as code
  • ADR new record if a decision warrants it
🔗 One branch, one PR. The plan, the code, the checked-off detail doc, and the flipped status row all land on richardh-feat-W#F# together — docs are never a separate commit afterthought. The Knowledge Graph then re-ingests them so the next feature's planning sees the new paper trail.
