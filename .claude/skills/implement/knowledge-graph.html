🕸️ Knowledge Graph — rev-eval local dev tool

A local, free graph over the codebase + docs/ (plans, feature specs, ADRs) for navigation and Q&A. Lives at tools/knowledge-graph/; run kg.py from there.

🚫 Not part of the deployed stack. It reads the repo read-only, stays out of the root docker-compose.yml and the gateway ROUTES, and is never auto-discovered. Purely a planning/navigation aid for the human + the /implement skill.

Two layers

The graph is split by cost: a deterministic structural layer that needs no model, and a semantic layer that does.

✓ no model · offline

Layer 1 — Structural

deterministic doc-graph

Parses doc conventions into a NetworkX graph of feature ↔ ADR ↔ plan ↔ spec ↔ code edges. Pure stdlib — works with Ollama down.

  • kg.py structure <node> — show a node's edges
  • kg.py export --format {mermaid,json,dot}
  • Fast, deterministic, always available
needs Ollama

Layer 2 — Semantic

LightRAG + embeddings

LightRAG entity/relation extraction + embeddings over prose → natural-language Q&A ("how was a similar feature built?"). Runs on containerized Ollama.

  • kg.py up → start Ollama (first run ~5GB)
  • kg.py ingest → build LightRAG index
  • kg.py query "…" → NL query (default hybrid)
  • kg.py down → free model RAM

What's in the graph (Layer 1 schema)

Node types

Feature W#-F# ADR ADR-0001 Plan docs/plans/ Spec days_*_features.md Code path (evidence)

Diagrams drop the ~190 code-evidence nodes for readability unless --include-code; JSON always includes them. Ambiguous code paths (bare main.py) stay (MISSING) rather than being guessed.

Edge types

DEPENDS_ONfeature → prerequisite feature
UNBLOCKSfeature → downstream feature
DECIDED_BYfeature → ADR (governing decision)
SPECIFIED_BYfeature → upstream spec section
DOCUMENTED_BYfeature → plan doc
EVIDENCED_BYfeature/doc → code path it cites
RELATES_TOgeneric cross-reference
LINKS_TOmarkdown link between docs

⭐ How it relates to /implement

The KG is touched at three points in the feature workflow — twice read during planning, once written after the push. See the full workflow →

Before · prerequisite
Related-feature lookup (optional, Layer 2)
Before planning, query the semantic layer — kg.py query "how was the scoring engine built?" — to find how similar features were implemented. Needs a prior up + ingest. This is what makes the KG worth keeping current.
Phase 1 · step 2 — read inputs
Ground the plan with Layer 1 structure
Automatic. The skill runs kg.py structure W#-F# (offline, deterministic) and uses the edges to: cross-check the detail doc's DEPENDS_ON/UNBLOCKS, pull governing DECIDED_BY (ADR) / SPECIFIED_BY (spec) / DOCUMENTED_BY (plan) into Context, and use EVIDENCED_BY code paths as the starting touchpoint list. It also runs structure <file> on files it intends to change for an impact check. Contradictions get flagged, not silently trusted.
Phase 2 · step 6 — after the push
Re-ingest so future planning sees the new work
Best-effort, not a gate. New plan / detail doc / ADR / FEATURE_STATUS row get folded back in. Layer 1 is automatic — it reads the repo live, so new docs already resolve. Layer 2 needs an explicit up → ingest → down. Deferred (not failed) if Docker/models are unavailable — the push already succeeded and Layer 1 is current regardless.
🔁 The virtuous loop: each completed feature re-ingests its docs → the next feature's query can find it → better-grounded plans over time. Skipping the re-ingest only degrades Layer 2 recall; Layer 1 never goes stale.

Command reference

# Layer 1 — no install, no model, works offline
python kg.py structure W4-F1            # a node's edges (also ADR-0001, a path, a label substring)
python kg.py export --format mermaid --out graph.mmd
python kg.py export --format json --out graph.json --include-code

# Layer 2 — semantic Q&A (use a venv on PEP-668 / Arch)
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python kg.py up                          # start Ollama + pull models (~5GB first run)
python kg.py ingest                      # index docs/ (+ evidence source files)
python kg.py query "Why was Jaccard chosen for multi-select scoring?"
python kg.py down                        # stop Ollama, free all model RAM

Memory, toggling & config

🔌 The "turn it off" switch

Ollama is one container behind the kg Compose profile, so root docker compose up never starts it. kg.py down removes the container — model RAM goes with it. Pulled models persist in the ollama-models volume, so re-up is fast.

💤 Idle auto-unload

While up, OLLAMA_KEEP_ALIVE (default 5m) keeps the model warm during use and auto-unloads after 5 min idle → RAM frees itself. Don't set KG_KEEP_ALIVE=0 during ingest (hundreds of calls; reload thrash).

⚙️ Models (env overrides)

LLM qwen2.5:7b-instruct, embed nomic-embed-text (dim 768). Override via KG_LLM_MODEL / KG_EMBED_MODEL / KG_EMBED_DIM.

🚀 GPU (optional)

CPU-only by default so up works anywhere. NVIDIA Container Toolkit + uncomment deploy.resources in docker-compose.kg.yml cuts ingest time dramatically.

🧱 Stack: NetworkX graph + LightRAG over containerized Ollama. Cognee was evaluated and rejected (leans on structured output, underperforms with small local models).
